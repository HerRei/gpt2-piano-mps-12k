Both models work on notes, not sound. MIDI is turned into event tokens, the model predicts the next ones, and a piano instrument plays the result.

The idea

Music that follows the game

I got the idea from a project a friend was doing at MIT. I wanted live piano music for PhantomHunt that reacts to what’s happening in the game. At first, the hardware it seemed to need was completely out of scope. So I started with a smaller question: could I train a model to continue a piano passage?

First: continue a passage

GPT-2 learned from piano performances on a borrowed Mac. It makes MIDI, and sometimes sounds wobbly. It gave me a place to start.

Then: measure the gap

Live music needs enough notes on time, room for the game to run, and a way to ask for quieter or busier playing.

Now: train with controls

RWKV-7 fits the measured speed budget. The first full epoch is running. Listening tests and the actual game test are still ahead.

Music is the prompt

Both versions generate MIDI: which notes to play, when, for how long and how loudly. A separate piano instrument makes the sound. There is no written prompt. This public repository contains the original GPT-2 code.

v1 · 2025–2026

GPT-2 on a borrowed Mac

I borrowed a friend’s M1 Max and trained a 12-layer GPT-2 from scratch with PyTorch MPS. MidiTok’s REMI format turns performances into musical events, with bars and positions to mark the beat.

The data was MAESTRO: almost 200 hours of competition piano. It is small for this task and full of virtuoso playing. The repository’s “12k” is a leftover working name, not the number of pieces.

It can continue a passage, but it is an offline continuation model. I cannot steer it while it plays. Training longer did not automatically help: epoch 2 had validation loss 1.43, versus 1.53 at epoch 4.

Measurements · October 2026

What it takes to play live

I measured how quickly the music consumes tokens, then timed models on an M1 Pro. A good continuation is not enough if it arrives after the note should have played.

The v1 note budget

REMI over 200 MAESTRO files needed about 40 tokens/s on average and 110 at the 99th percentile of one-second windows. The 87M GPT shape at 2,048 context managed 35 tokens/s on PyTorch CPU. It could not keep up even on average.

One token, fixed-size state

RWKV-7 carries a fixed-size recurrent state from one token to the next. A GPT’s attention history needs a cache. Moving that cache on every call was costly, and keeping it inside the model did not compile for the Neural Engine in my tests.

Room for the game

Aria’s tokenizer uses about three tokens per note. That gives about 12 ms per token for the 99th-percentile second. The 94M RWKV-7 step model took 3.5 ms median and 4.2 ms p99 with int8 weights on the M1 Pro Neural Engine.

These are batch-one speed tests with random weights, not a listening test or an in-game benchmark. The real RWKV-7 step model was measured on 7 October. The earlier REMI budget and PyTorch CPU result were measured on 4 October.

v2 · Training now

RWKV-7 with intensity controls

I came back to the game idea with a 94M-parameter RWKV-7. I trimmed Aria’s tokenizer to piano, with a vocabulary of 2,176 tokens including 13 density and loudness control tokens.

The pruned Aria-MIDI dataset has about 4.6 billion tokens. It gives this run much more music to learn from than MAESTRO. I train on two AMD GPUs in my desktop: a Radeon RX 9060 XT and a Radeon VII, using ROCm and one process per card. Together they measured about 29.7k tokens/s, or an estimated 43 hours per epoch.

Learn controls from the music

Every five seconds, the model gets density and loudness tokens computed from the coming music. During training, 15% of controls are dropped. That lets classifier-free guidance compare controlled and unconditioned predictions at runtime.

A small, matched comparison

At about 28M parameters and 250M training tokens on the same data, RWKV-7 reached validation loss 2.172. A GPT with rotary positions reached 2.258. That supported the choice of RWKV-7; it does not prove the final music will be better.

Controls respond, then fade

In fresh-state tests, density landed in the requested level 69–97% of the time. Soft versus loud gave MIDI velocities of 32 versus 99. But in long streams, “dense” fell from 9 notes/s in minute one to about 5 after 10–30 minutes.

Guidance held the controls in the small runs

Comparing requested and contrasting controls at guidance strength 1 kept “dense” at 11 notes/s and “medium” at 2 at minute 15. This was a two-pass guidance experiment. The full run adds control dropout for classifier-free guidance, whose strength still needs tuning. Two passes would cost about 7 ms per token at 94M; that is an estimate, not an end-to-end game measurement.

Status · 8 October 2026

The first epoch is running

I expect it to finish around 9 October. Next come listening tests, Core ML and ONNX exports of the trained checkpoint, and a test inside PhantomHunt.

The plan is to generate one or two seconds ahead. Controls apply at the next five-second segment. A simple rule layer can change velocity or thin notes immediately, while a game “conductor” brings themes back.

Notes

Limitations

v1

Local artifacts

Datasets and checkpoints are not included in the repo.

Prompt sensitivity

Output quality depends on the MIDI prompt and the checkpoint being sampled.

Random split

The split is random by file, not MAESTRO's official one, so related pieces can land on both sides and flatter the validation loss.

Experimental control

The Melody Intensity Editor is still a side experiment and only works on short phrases.

v2

Not finished

Training is still running. The numbers above come from small test runs, not from the final model.

No long-form structure

On its own it keeps playing but doesn't build themes. The game needs a "conductor" that re-seeds themes and sets the controls.

Non-commercial data

Aria-MIDI is CC BY-NC-SA, like MAESTRO, so the model is for non-commercial use only.

Code not public yet

The repository linked here is v1. The v2 code isn't public.
